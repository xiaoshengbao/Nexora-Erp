# 局域网固定主机实机验收

此清单用于首版内部试用。请使用测试实例及测试数据，在 Windows x64 和 Apple 芯片 Mac 上安装各自生成的安装包，并记录系统版本、安装包提交号及结果。CI 和单机检查不能替代以下跨机结果。

## 连接组合

| 固定主机 | 客户端 | 预期结果 |
| --- | --- | --- |
| Windows x64 | Windows x64 | 发现或输入局域网地址，核对指纹后登录并读取库存 |
| Windows x64 | macOS Apple 芯片 | 同上 |
| macOS Apple 芯片 | Windows x64 | 同上 |
| macOS Apple 芯片 | macOS Apple 芯片 | 同上 |

每个组合都需确认：首次连接前只展示证书指纹，核对后才能保存信任；退出客户端重新打开可自动连接；更换主机证书后自动连接被阻止，界面要求再次核对。

## 主机生命周期

1. 在主机上创建测试实例，完成管理员初始化。记录服务状态、实例名称、端口和证书指纹，不记录密码。
2. 关闭桌面窗口并完全退出桌面应用。客户端仍能发现并访问服务，库存读写正常。
3. 重启主机，在**无人登录**时从另一台设备访问健康接口和已保存的连接；登录主机后确认服务状态仍为运行中。
4. 在主机设置中停止服务。客户端应显示断线，禁止新编辑提交；重新启动服务后自动恢复读取，必要时重新登录。
5. 断开主机网络再恢复，检查客户端的断线提示、发现结果和重连。让测试主机获得新局域网地址，确认客户端只在原实例 ID 与证书指纹一致时自动更新保存的地址；证书变化时不得自动连接。网络广播受阻时再测试手动地址连接。
6. 两台客户端同时登录，交替创建测试入库单并确认；检查库存流水、来源单据和最终数量一致。

## 升级与恢复

1. 在升级前记录测试库存和证书指纹，使用设置中的升级入口；确认升级前备份包含 `nexora.db`、`server.crt`、`server.key`，服务重新运行后数据与指纹不变。
2. 停止服务，将备份恢复到**新的**数据目录；按 [后端恢复说明](../backend/README.md#固定主机管理与升级) 指向该目录后启动，核对测试库存与原证书指纹。
3. 尝试把损坏或缺少证书的备份恢复到新目录；应明确报错，且不得留下可误用的部分实例。
4. 在测试实例上用无法正常启动的服务程序演练失败升级：界面应报错，macOS 新版 LaunchDaemon 作业被卸载，旧版程序和服务恢复；核对原库存及证书指纹。

只有上述全部组合和步骤有实机记录后，才将首版局域网交付标为已验收。签名、公证、自动更新及 Intel Mac 不在本轮验收范围。

## Windows 自动检查范围

Windows x64 CI 先运行全部后端和桌面单元测试，随后由 `scripts/smoke-windows.ps1` 检查打包服务程序的 HTTPS、系统服务安装与启停、进程异常退出后的 SCM 自动恢复、升级、成组备份和恢复。脚本在临时实例中写入测试管理员与供应商，强制结束服务进程后要求系统以新 PID 自动拉起，并分别从异常恢复、手动重启、升级及恢复后独立启动的服务经业务接口重新登录并读取供应商，同时核对原证书未变化。它能发现 Windows 打包、服务权限、故障恢复策略和资料恢复的回归，但运行器不会经历无人登录的物理主机重启，也不能证明两台设备间的连接与发现。

打包桌面首次进入页检查允许窗口导航期间单次 CDP 请求超时，并在 30 秒总时限内以新请求 ID 重试；旧请求的迟到响应不会冒充新结果。页面脚本异常、调试连接中断以及最终入口或告警内容错误仍直接判失败。此调整针对 Windows CI 曾出现一次 5 秒页面检查超时、同一提交重跑通过的情况，不改变实机验收范围。

## macOS 当前用户域后台恢复检查

安装后端依赖并生成打包服务后，在 Apple 芯片 Mac 上可运行 `.venv/bin/python scripts/smoke-macos-launchd.py`。脚本将打包服务复制到临时安装式目录，在当前用户的 launchd 域中启动一次性实例，确认 HTTPS 健康接口可访问，然后强制终止服务进程并确认 launchd 拉起新进程；结束时卸载作业并清理临时资料。2026-09-28 在上述设备上首次手工检查通过，服务进程 PID 从 61227 变为 61328，两次健康检查均成功。

该检查使用当前用户域，**不等于**系统级 LaunchDaemon 安装、无人登录开机启动或跨设备验收。正式服务仍需在管理员授权后按本清单逐项实测。

安装包流水线还用独立随机标签在系统 launchd 域注册临时 LaunchDaemon，确认启动、进程异常退出后的自动恢复，以及卸载后的 HTTPS 停止访问；测试不会操作机器上已有的正式服务。系统域检查仍不能证明真实设备在**无人登录时重启**后的可用性。

在确认一次性 Mac CI 主机没有已有 Nexora 系统资料后，流水线还使用打包程序演练正式系统路径的安装、停止、重启、正常升级与升级前备份，以及新版程序无法启动时的回退；每次恢复后都经 HTTPS 重新登录读取测试供应商，并核对证书与旧程序。此演练会清理它创建的临时服务，不在已有真实主机上运行。真实设备升级和无人登录重启仍需按上文验收。

macOS 停止服务后会等待 launchd 完全卸载同名作业，再返回停止成功或继续升级，以免立即重新注册时发生冲突；超时会明确报错。本项仍以系统域流水线结果和真实设备操作记录分别判定。

macOS 安装包流水线另运行 `scripts/smoke-macos-backup.py`：使用安装包内服务程序启动临时 HTTPS 实例，创建测试管理员与供应商，在服务运行时备份数据库和证书，恢复到新目录并重新登录读取供应商；篡改散列值的归档必须被拒绝且不留下恢复目录。此检查覆盖打包程序的恢复链路，不代替实际主机升级、无人登录重启或跨设备验收。

## 2026-09-28 Windows 主机到 Mac 客户端的发现检查

Windows 主机位于 `192.168.3.191:8000`，Mac 客户端位于 `192.168.3.5`。Mac 系统的 mDNS 工具能收到该 Windows 主机的 `_nexora._tcp` 广播；广播同时包含 6 个 IPv4 地址，物理网卡地址排在多个虚拟网卡地址之后。原客户端只检查首个地址，因此扫描页不显示这台主机。Mac 到主机的 TCP 连接成功，使用服务证书核验的 `GET /api/v1/server/info` 返回 HTTP 200、匹配的实例身份、版本 `0.1.0` 和已初始化状态。

客户端改为核验同一广播的全部局域网 IPv4 地址后，Mac 开发版的扫描结果显示 `192.168.3.191:8000` 在线；点击该结果进入首次证书指纹核验页，尚未确认信任。**本记录只验证发现、公开身份接口和进入核验页**，尚未完成 Windows 屏幕指纹比对、登录读取库存、关闭窗口后访问或主机重启验收。已安装的旧客户端仍需升级或暂用手动地址连接。

同日再次检查发现，Mac 上的服务同时广播虚拟环回地址 `172.30.195.124` 与当前网卡地址 `192.168.3.5`；原先按最快响应选择时，扫描结果使用了虚拟地址。客户端改为优先核验当前非环回网卡同网段地址后，在同一局域网的开发版界面中，Mac 服务显示 `192.168.3.5:8000`，Windows 服务显示 `192.168.3.191:8000`。检查脚本以服务提供的证书建立 TLS，核对公开接口、证书与广播中的实例身份一致；这不替代首次连接时从服务端电脑核对指纹。此项验证了新扫描的地址选择，尚未覆盖跨设备登录。

同日使用隔离的客户端资料目录，先从 Mac 测试服务的公开接口读取实例身份和证书，再把连接记录中的地址设为不可用的 `192.168.4.191:8000`，保留原实例 ID 与证书指纹。启动本轮构建的 Electron 客户端后，连接记录自动更新为广播中经 TLS 核验的 `192.168.3.5:8000`，实例 ID 未变。隔离客户端退出后已清理测试资料。这验证了**Mac 单机实际启动时的旧地址恢复**；没有改变真实用户连接记录，也不能代替主机实际换 IP、Windows 客户端或跨设备登录验收。

## 2026-09-28 Mac 已安装主机的隔离客户端重连检查

在同一台 macOS 27.0 Apple 芯片设备上，使用基于 `bbc3918` 构建的本机 arm64 应用包及全新的隔离客户端资料目录，连接当前已安装的 Mac 系统服务；没有替换 `/Applications` 中的程序或修改主机数据。客户端扫描结果同时显示 Mac 的 `192.168.3.5:8000` 和 Windows 的 `192.168.3.191:8000`。选择 Mac 实例后进入“服务端已就绪”，并可打开登录页；客户端保存的证书 SHA-256 指纹与主机数据目录中的证书独立计算结果一致。

本机安装版会先核对系统服务数据目录中的证书与端口实际提供的证书，再建立本机信任，因此这个**同机**连接没有显示远程客户端的首次指纹确认页。退出隔离客户端并确认其进程结束后，用同一资料目录重新启动，应用直接恢复到该 Mac 主机的登录页。测试进程退出后，系统 LaunchDaemon 仍为 `running` 且服务 PID 保持 `63286`；隔离资料已移入废纸篓。

本次没有输入账号密码或读取库存，也没有从另一台设备连接 Mac 主机。它只补充当前已安装主机的同机连接和客户端重启证据；跨设备指纹核验、登录、无人登录重启及其余验收步骤仍待实测。

## 2026-09-28 Windows 窗口关闭后的跨设备发现检查

Windows 电脑操作者关闭 Nexora 桌面窗口后，右下角托盘图标随桌面进程消失。此时 Apple 芯片 Mac 到 `192.168.3.191:8000` 的 TCP 连接仍成功，服务公开身份接口返回 HTTP 200，macOS 的 Bonjour 浏览结果仍包含 Windows 实例 `Nexora-8ff66f4e-b344-42cb-bf63-9bed2e85007d`。使用全新隔离资料目录启动本机打包的 Mac 客户端，扫描页继续显示该 Windows 地址为在线；选择后进入首次证书核验页，未勾选核验时连接按钮禁用。测试后退出隔离客户端，未保存对 Windows 实例的信任。

这证明**Windows 桌面窗口关闭后，另一台真实设备仍能发现该主机并到达连接前核验**。托盘图标消失不能说明服务已停止；Windows 本机 `NexoraERPHost` 服务状态、指纹的独立比对、登录与库存读写、无人登录重启仍待设备操作者核实。公开接口的 HTTP 200 本身不作为证书身份核验结果。

后续桌面代码已调整为 Windows 关窗后保留托盘，并在菜单中展示本机服务状态、提供手动刷新与重新打开窗口入口。上段是旧安装包的实测现象；新行为尚需在更新后的 Windows 安装版上操作验证，不能把代码和构建结果写成设备验收通过。

Windows 升级时的目录替换会在 SCM 停止后对 WinError 5/32/33 最多等待 10 秒。短暂占用消失后继续升级；持续占用仍明确失败，并恢复原服务。单元测试覆盖这两条路径及数据、备份和旧程序保留，不把重试机制视为真实主机升级验收完成。
